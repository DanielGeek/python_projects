# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault: a web platform for playing arcade games online and competing for the highest score. Built with spec-driven design (`/spec` and `/spec-impl` skills, installed via `npx skills@latest add Klerith/fernando-skills`). Specs and docs must be written in English. The UI copy and game data in `lib/games.ts` are in English.

## Commands

- `npm run dev` — dev server (Turbopack)
- `npm run build` / `npm start` — production build / serve
- `npm run lint` — ESLint (flat config, `eslint.config.mjs`)
- `npm run format` — Prettier over the whole repo (config `.prettierrc.json`, ignores `.prettierignore`).
- `npm test` — Vitest, single run (`npm run test:watch` for watch mode). Tests sit next to the code as `*.test.ts` (e.g. `lib/contact.test.ts`); import `describe/it/expect` from `"vitest"`. `lib/test-support.ts` has `installFakeWindow()`, a fake `window` with localStorage (`failReads` and `failWrites` simulate blocked storage) used by the `lib/*.test.ts` files. `lib/games.test.ts` checks `GAMES` against the `readers` in `public/games/bridge.js` and the `av-cover-<id>` rules in `app/globals.css`, and each game's `touch` config: every button code must appear in that game's `game.js` and in the `KEYS` allowlist of `bridge.js`, `a` and `b` must exist, no code may repeat, `move` may only hold arrows and `extra` at most three buttons.
- Dev launch: `.claude/launch.json` has the `arcade-vault` config (`npm run dev`, port 3000).
- Notification hook: `.claude/settings.json` also plays `assets/claudecode-finished.mp3` with `afplay` (macOS) on `Notification`.
- Format hook: `.claude/hooks/format.sh` runs as a `PostToolUse` hook (`Write|Edit`, in `.claude/settings.json`). It runs Prettier on the written file, then `eslint --fix` for `.ts/.tsx/.js/.jsx/.mjs/.cjs`. Remaining ESLint errors exit 2 so Claude sees them. Skips `public/games/`, `references/`, `.claude/` and build output.

## Architecture

- `app/` — App Router. Routes: `/` (landing), `/library` (game library), `/game/[id]` (detail), `/game/[id]/play` (player), `/about` (About + contact form), `/login` (sign in, sign up, guest; SPEC 15), `/hall-of-fame`, plus the Route Handlers `POST /api/contact`, `GET /api/health/supabase` and `GET /auth/confirm` (verifies the email confirmation link). Main files: `library/library.tsx`, `game/[id]/page.tsx` with `game-stats.tsx` and `game-scores.tsx`, `game/[id]/play/` (`game-player.tsx`; on a touch device, `(pointer: coarse)` through `useCoarsePointer`, it hides the HUD, shows a thin Pause and Exit row above the CRT bezel and draws `TouchControls` (the Gamepad MK-II pad, SPEC 13) right below the CRT bezel, never over the canvas, only while the game is playing, loaded and the final-score modal is closed; SPEC 12), `hall-of-fame/hall-of-fame.tsx` (game tabs that wrap, SPEC 07) and `login/auth-card.tsx` (email + password sign in; username + email + password sign up, then a "Check your email" screen with "Resend confirmation"; it reads `?error=confirm` through `useSearchParams`, so `login/page.tsx` wraps it in `Suspense`). Anything that means "back to the library" links to `/library`; the logo links to `/`.
- `app/_home/` — landing sections, one file each: `hero`, `features`, `games-rail`, `stats`, `activity`, `pricing`, `final-cta`, plus `silhouettes`, `section-head` and `reveal` (client wrapper that fades a section in once, using `IntersectionObserver`). `hero` and `pricing` read `useSession` to hide "Create account" and turn "Start free" into "Play now". `stats` and `pricing` are static marketing copy; `activity` shows real scores. The `_` prefix keeps the folder out of routing. Landing CSS is `av-home-*` in `app/globals.css`, ported from `references/templates/home-about/`. `games-rail` shows the first five games, hides the `+N more` line when there are none, and its big tile fills the row when it is the only game.
- `app/about/` — About page: `highlights`, `divider` and `contact-form` (client; `ContactSection` validates with `validateContact`, posts JSON to `/api/contact`, shows the `[ERR]` line on failure and the `VAULT-OS // TERMINAL` screen on success). It reuses `Reveal` from `app/_home/`. CSS is `av-about-*` in `app/globals.css`, ported from `references/templates/home-about/`.
- `app/api/contact/route.ts` — `POST` Route Handler that emails the contact form through Resend. Order: parse JSON (400), honeypot field `website` (200, no email), `validateContact` (400 with `fieldErrors`), env check (500), Resend send (502 on error). `from`, `to` and the key come only from env vars; `replyTo` is the visitor's email. Plain-text body. `GET` answers 405.
- `app/api/health/supabase/route.ts` — `GET` Route Handler that checks the Supabase connection by running `select id from games limit 1` through the server client (5 s timeout), so it proves the URL, the key and the `games_and_scores` schema. Answers `200 { ok: true }`, or a generic `500` with no URL, key or stack (details go to `console.error`). It uses `await connection()` and exports neither `runtime` nor `dynamic`, because `cacheComponents` rejects both. Other methods answer 405.
- `components/ui/` — shared UI primitives (`basics.tsx` has `cx` and base components; `interactive.tsx` has client components such as `Input` and `SearchBar`; `game.tsx` has `GameCard`, `CoverArt`, `HUD`, `CRTScreen`, `Podium`, `Leaderboard`; `navbar.tsx` has the Nav with the credit balance and calls `purgeRemovedGameScores`; `touch-controls.tsx` has `useCoarsePointer` and `TouchControls`, the Gamepad MK-II pad right below the CRT screen: a shell, a four-key D-pad with hub and pulsing gem where unused directions are drawn disabled and without `data-key`, round B (always cyan) and A (game accent) with a dashed ring while pressed, and small pills for `extra`, in the centre of the shell on a wide screen and in a full row under the pad below 620 px; SPEC 12 for the behavior, SPEC 13 for the look; CSS is `av-touch-*`, ported from `references/gamepad-assets/`). Per-game cover art is CSS only: `av-cover-<gameId>` in `app/globals.css`. They use `av-*` CSS class names defined in `app/globals.css`.
- `lib/` — client-side data layer, all stand-ins for a future backend:
  - `games.ts` — static `GAMES` catalog (Asteroids, Drop, Brick Buster, Snake and Froggy: SPEC 08 cut it to Asteroids, SPEC 09 brought Drop back, SPEC 10 brought Brick Buster back, SPEC 11 added Snake as a new game, not a restore of the archived `serpent`, and SPEC GJ froggy-01 brought Froggy back from the archive, written from scratch), `CATEGORIES` (built from `GAMES`, so it is `All`, `Shooter`, `Puzzle` and `Arcade`), `getGame`. Accents: cyan, magenta, yellow, green. `difficulty`, `plays` and `tags` feed the detail stat strip (`plays` is mock data). `src: null` means a game is listed but not playable yet; no entry has it now. The optional `touch` field (`TouchControls`: `move`: the D-pad directions the game uses, `a`: main action, `b`: second action, optional `extra`: up to three small pills; each is a `TouchButton { code, label, name, repeat? }`) describes the on-screen buttons of a game; `code` is a `KeyboardEvent.code` the game already handles. `repeat: true` makes the host resend `keydown` while held (after 250 ms, every 90 ms) for games that move once per keydown, like `drop`. All five games have it (SPEC 12). `froggy` has no `repeat`, because one press on a pad button is one hop; its `A` and `B` are `Space` and `Enter`, both start or restart, since the test needs two different codes.
  - `games-archive.ts` — `ARCHIVED_GAMES`: the five games removed by SPEC 08 that have not come back (serpent, muncher, invaders, rocks, pixel-duel; `drop` returned with SPEC 09, `brick-buster` with SPEC 10 and `froggy` with SPEC GJ froggy-01; `snake` of SPEC 11 is a separate game, so `serpent` stays here), kept as data and imported by nothing but its test. To bring one back, move its entry to `GAMES`, add a migration that inserts its `games` row and, for a playable one, check its folder in `public/games/`, its `readers` entry and its `av-cover-<id>` rule.
  - `session.ts` — the session, exposed via `useSession` (`useSyncExternalStore`, returns `Session | null` with `{ name, guest, userId? }`). An account comes from Supabase Auth (SPEC 15): the first subscriber (`subscribe`) attaches `onAuthStateChange`, and the username is read from the own `profiles` row. A guest is a local session in localStorage (`arcade-vault:session`) named `GUEST` and never touches Supabase. Only one exists at a time: an account clears the guest, and `playAsGuest` (async) signs out of Supabase first. `signOut` is async too. A signed-in user with no `profiles` row is treated as signed out (`console.error`). If the Supabase variables are missing, the app keeps working with guests only.
  - `auth.ts` — SPEC 15. Pure `validateSignUp` / `validateSignIn` (username `^[A-Za-z0-9_]{3,12}$` and never `GUEST`; email; password 8 to 72 characters; sign in only checks that fields are filled) and wrappers over the browser client that never throw and return `{ ok: true } | { ok: false, code }` with `AuthFailure` = `username_taken | invalid_credentials | email_not_confirmed | network | unknown`: `signUpWithEmail` (calls the `username_available` RPC first, then `signUp` with the username in `options.data`), `signInWithEmail`, `resendConfirmation`, `signOutEverywhere`. `toAuthFailure` maps Supabase errors.
  - `credits.ts` — per-device credit counter in localStorage (`arcade-vault:credits`, starts at 3), exposed via `useCredits`, `spendCredit`, `insertCoin`. The player spends one credit per game start (mount and "Play again"); at 0 it shows `INSERT COIN` instead of the game. The Nav shows the balance.
  - `scores.ts` — per-game leaderboards in localStorage (`arcade-vault:scores:<gameId>`, top 50). `useScores` subscribes to a custom `arcade-vault:scores` event plus `storage`. Cross-game helpers for the landing: `useAllScores`, `latestScores`, `topPlayersToday` (best score per player, local calendar day) and `timeAgo`. `purgeRemovedGameScores` removes the lists of games that are not in `GAMES` (SPEC 08); `components/ui/navbar.tsx` calls it once per page load. It only looks at `arcade-vault:scores:*` keys, never at the session or the credits.
  - `contact.ts` — `LIMITS` (name 80, email 254, message 2000) and `validateContact`. Pure functions shared by the contact form and `POST /api/contact`; the route is the authority.
  - These modules carry `BACKEND:` comments marking where the real API or Supabase calls should replace the localStorage code. Keep the exported function signatures stable when swapping. `lib/supabase/` is the foundation for that swap. `leaderboard.ts`, `auth.ts`, `session.ts`, the health route and `/auth/confirm` use it (SPEC 06, SPEC 08, SPEC 15); credits are a future spec, and the local `scores.ts` still feeds `/library`, `/game/[id]` and the landing.
  - `leaderboard.ts` — global scores in Supabase: read in SPEC 06, written in SPEC 08. `fetchTopScores(gameId)` returns the top 50 of `scores` as `{ ok: true, entries: ScoreEntry[] }` or `{ ok: false }` (never throws); `rowToEntry` maps a row to `ScoreEntry`. `/hall-of-fame` reads with `fetchTopScores`, with loading, `[ERR]` + `Retry` and empty states and no localStorage fallback. `submitScore({ gameId, player, score, userId? })` inserts one row from the browser with the publishable key and resolves `true` or `false` (never throws); `toScoreRow` returns `{ game_id, player, score, user_id }`: with a `userId` it trims the name and cuts it to 20 characters, and rejects an empty name; without one the score is a guest's and `player` is always `GUEST`. It also rejects a score that is not an integer from 0 to 9,999,999. `game-player.tsx` calls it after the local `saveScore`, with `SAVING…`, `SCORE SAVED` and an `[ERR]` line when it fails (the local copy is kept). Since SPEC 15 the final-score modal has no name field: an account saves under its username and `userId`, a guest as `GUEST`. RLS enforces both, so an account cannot be forged, but a guest score can still be posted by calling the REST API directly (any score in range, as `GUEST`). `/library`, `/game/[id]` and the landing still read the local `useScores`.
- `lib/supabase/` — Supabase connection only (SPEC 04). `env.ts` has `getSupabaseEnv`, which reads and validates the two public variables and throws an error naming the missing one. `client.ts` exports `createClient()` for Client Components (`createBrowserClient`). `server.ts` exports async `createClient()` for Server Components and Route Handlers (`createServerClient` with `await cookies()`). Both create the client inside the function, never at module load. There is no `proxy.ts` and no service role key yet; the browser client refreshes the token by itself.
- `supabase/migrations/` — SQL migrations, versioned in git and applied with the Supabase MCP (`apply_migration`). The file name carries the version that Supabase assigns (check `list_migrations`). Eight so far. `20261019092211_games_and_scores.sql` (SPEC 06) creates `games` and `scores` with RLS on and `select` policies, and seeded them with invented data. `20261019103546_save_scores.sql` (SPEC 08) deleted that seed and every game except `asteroids`, and added the `insert` policy on `scores` (player 1 to 20 characters after trimming, score 0 to 9,999,999; the foreign key keeps scores to games that exist in `games`). `20261019103728_least_privilege_grants.sql` revokes every privilege of `anon` and `authenticated` on both tables and grants back only `select`, plus `insert` on `game_id`, `player` and `score` of `scores`, so `update`, `delete` and `truncate` are not granted at all and the browser cannot set `id` or `created_at`. `20261019184002_add_drop_game.sql` (SPEC 09) inserts the `drop` row in `games`, the same values as the SPEC 06 seed. `20261019230130_add_brick_buster_game.sql` (SPEC 10) does the same for `brick-buster`. `20261020000246_add_snake_game.sql` (SPEC 11) inserts the `snake` row. `20261022131344_add_froggy_game.sql` (SPEC GJ froggy-01) inserts the `froggy` row, with accent yellow (the SPEC 06 seed had it green). `20261023190518_auth_profiles.sql` (SPEC 15) creates `profiles` (`id` references `auth.users`, `username` upper-case `^[A-Z0-9_]{3,12}$` and not `GUEST`, unique; RLS on, `authenticated` may `select` only its own row, no write grants), the trigger `on_auth_user_created` (`handle_new_user`, `SECURITY DEFINER`, reads `username` from the sign-up metadata), the RPC `username_available(name)` (`SECURITY DEFINER`, executable by `anon` and `authenticated`: its two advisor warnings are intended, the sign-up form needs it), `scores.user_id` (null for guests and for every older row), and replaces the open insert policy with two: `anon` may insert only `user_id is null` and `player = 'GUEST'`; `authenticated` only `user_id = auth.uid()` and `player` equal to its own `profiles.username`. `scores` now holds only scores that players saved. Adding a game to `GAMES` needs a new migration that inserts its `games` row; `lib/leaderboard.test.ts` rebuilds `games` from the migrations and fails when it differs from `GAMES`. Known and not ours: `public.rls_auto_enable()` is a `SECURITY DEFINER` function that `anon` and `authenticated` can execute (advisor warning), pending its own spec.
- `public/games/<id>/` — playable games are static HTML/canvas copies of sibling projects, embedded in the host page via iframe. They are not part of the React build. `asteroids`, `drop`, `brick-buster`, `snake` and `froggy` are in the catalog (`snake` and `froggy` are not copies: they were written for SPEC 11 and SPEC GJ froggy-01); the folder of `rocks` stays on disk, unlisted, until that game returns from `lib/games-archive.ts`. `asteroids` has an 800×600 canvas that was cut at the right edge on a phone, so its `index.html` (not its `game.js`) has an inline `fitToFrame()` that scales the canvas with CSS `zoom` and never up (SPEC 12). `drop` is bigger than the 4:3 CRT frame (its page is about 662×656 px), so its `game.js` has `fitToFrame()`, which scales the page down with CSS `zoom` to fit the iframe and never scales up; a game whose page does not fit the frame needs the same. Its keydown handler also calls `preventDefault` on the arrow keys so they do not scroll the host page. `brick-buster` has an 800×600 canvas that is cut at 375 px, so its `game.js` has the same `fitToFrame()`, sized from the canvas and not from the page because its controls guide and mute indicator sit outside the canvas; its keydown handler calls `preventDefault` on `ArrowUp` and `ArrowDown` outside the menu. Its own `blur` handler pauses it when the iframe loses focus, so after the host Pause and Resume it stays paused until P or Esc. `snake` has a square 600×600 canvas (`aspect: "1 / 1"`, 20×20 grid) and the same `fitToFrame()`, sized from the canvas; it uses `requestAnimationFrame` and `performance.now()`, so the host pause freezes it, and it does not pause on `blur`. Its `sprites.js` and `fruits.png` are third-party sprites ripped from Google Snake (spriters-resource), with the atlas names fixed to match the image; replacing them with original art would need its own spec. Its reader returns `lives: null` and `over: state === 'gameover'`, which is also true after a win. `froggy` has an 800×600 canvas (`aspect: "4 / 3"`, a 16×12 grid of 50 px cells) and the same `fitToFrame()`, sized from the canvas. It is written from scratch with all art drawn on the canvas (no image or audio file) and is the only game with swipe: pointer events on the canvas, `touch-action: none`, one hop per swipe of 30 px or more, and a tap that hops up or starts the run. It uses `requestAnimationFrame` and `performance.now()`, so the host pause freezes it and its timer, and it does not pause on `blur`. Its reader returns `lives` and `over: state === 'gameover'`, the only way a run ends. SPEC 14: its glowing parts (logs, vehicles, pads, life icons and the neon frame) are painted once per palette into offscreen canvases and copied with `drawImage` (`sprite`, `stamp`, `drawPad`, `drawLife`, `drawPost`), only for the skins with `stamp: true` (`classic` and `neon`); the cache is cleared in `refreshAppearance()`, and the frog is not cached. Without a GPU this took Froggy from about 10–17 to about 40 FPS in `classic`.

Performance (SPEC 14, `references/performance-baseline.md`): the protocol, the frame counter snippet, the budgets (p95 under 20 ms at CPU 4x on desktop, 50 FPS on a phone) and the before/after tables live there. A Chrome with a GPU hides canvas costs (everything reads 60 FPS) and CPU throttle does not slow down rasterization, so measure in the installed Chrome and also in a no-GPU Chrome for Testing, each game standalone (`/games/<id>/index.html`) and inside the host. Rules learnt: do not call `shadowBlur` for shapes without glow and reset it to 0 after a glowing shape; do not rebuild gradients, font strings or arrays inside the frame loop; cache glowing parts that do not change (see Froggy) instead of blurring them every frame; a cache must be cleared when the skin or theme changes. In the host, the animated floor grid of the page background is paused on `/game/<id>/play` (`.av-app:has(.av-player) .av-backdrop-floor::before` in `app/globals.css`) because repainting it behind the game was the only host cost with a measured gain; animating it with a `transform` instead did not help. SPEC 14 closed with Froggy and the host; the `game-performance-booster` agent checked the other four on 2026-10-22 (`drop`, `snake` and `asteroids` got a neon cache, `brick-buster` was within budget; see `references/game-performance.md`). Nothing has been measured on a real phone (`n/m`).

## Environment variables

Copy `.env.template` to `.env` (git-ignored). Server only, never prefix with `NEXT_PUBLIC_`:

- `RESEND_API_KEY` — Resend API key.
- `CONTACT_TO_EMAIL` — inbox that receives contact messages.
- `CONTACT_FROM_EMAIL` — sender, e.g. `Arcade Vault <onboarding@resend.dev>`. The Resend sandbox sender only delivers to the email that owns the Resend account.
- `SUPABASE_DB_PASSWORD` — database password, reserved for the Supabase CLI. No code reads it.

If any of the first three is missing, `POST /api/contact` answers 500.

Public by design (the `NEXT_PUBLIC_` prefix is intended here; security comes from RLS, not from hiding them):

- `NEXT_PUBLIC_SUPABASE_URL` — project URL, `https://<project-ref>.supabase.co`.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — publishable (anon) key. Never put the service role key in a `NEXT_PUBLIC_` variable.

If either is missing or the URL is not `http(s)`, `getSupabaseEnv` throws and `GET /api/health/supabase` answers 500.

Supabase Auth setup lives in the dashboard, not in the repo (SPEC 15): custom SMTP through Resend (`smtp.resend.com`, port 465, user `resend`, the Resend API key as password; the sandbox sender `onboarding@resend.dev` only delivers to the email that owns the Resend account), Site URL `http://localhost:3000` with redirect URLs for every host in use (including the `NEXT_PUBLIC_LOCAL_URL` host), "Confirm email" on, and the "Confirm sign up" template link `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`. The default `{{ .ConfirmationURL }}` link does not work with `/auth/confirm`.

Development on a phone over the network (they only hold a local address): `NEXT_PUBLIC_LOCAL_URL` (for example `http://192.168.1.170`) and `NEXT_PUBLIC_PORT` (`3000`, a note of the dev port: no code reads it). `next.config.ts` reads the hostname of `NEXT_PUBLIC_LOCAL_URL` into `allowedDevOrigins`, because Next blocks dev assets for any origin other than `localhost`, and without it the page loads on the phone but never hydrates (the menu does not open and the game stays on "Starting game"). Next matches the hostname only, so the scheme and the port are dropped, and an unset or invalid value allows nothing extra. Restart `npm run dev` after editing them. `NEXT_PUBLIC_*` values are inlined at build time: restart `npm run dev` after editing `.env`, and rebuild for production.

### Host ↔ game bridge

`public/games/bridge.js` is loaded by each game's `index.html` **before** its own scripts, with `data-game="<id>"` on the script tag. It:

- Polls the game's top-level globals every 200 ms (per-game `readers` map) and posts `{source: 'arcade-vault-game', type: 'state', game, state: {score, lives, level, over}}` to the parent window.
- Pauses/resumes on host messages `{source: 'arcade-vault-host', type: 'pause' | 'resume'}` by freezing `requestAnimationFrame` and `performance.now`.
- Turns host messages `{source: 'arcade-vault-host', type: 'key', code, down}` into a `keydown` (`down: true`) or `keyup` `KeyboardEvent` on `document` with `bubbles: true`, for the touch controls. Only `e.source === window.parent` is accepted, and only codes in the `KEYS` allowlist (`ArrowUp/Down/Left/Right`, `Space`, `Enter`, `KeyC`, `KeyE`, `KeyP`, `Digit1` to `Digit3`); any other code is ignored. A new touch button needs its code in that table. The host owns key repeat, since a synthetic `keydown` does not auto-repeat, and releases every held key on `pointerup`, `pointercancel`, `lostpointercapture`, page hidden, host pause and unmount. The touch buttons call `preventDefault` on `pointerdown` and `mousedown` so the tap does not take the focus from the iframe: `brick-buster` pauses on `blur`.

Adding a new playable game requires: its folder under `public/games/`, the bridge script in its `index.html`, a `readers` entry in `bridge.js` that matches the game's global state variable names, a `src` and a `touch` config in `lib/games.ts` (`lib/games.test.ts` fails without it, and when a code is not in the game's `game.js` or in the bridge allowlist). Any new catalog entry also needs an `av-cover-<id>` rule in `app/globals.css`, and a migration that inserts its row in `public.games`, because saved scores have a foreign key to it.
