# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault: a web platform for playing arcade games online and competing for the highest score. Built with spec-driven design (`/spec` and `/spec-impl` skills, installed via `npx skills@latest add Klerith/fernando-skills`). Specs and docs must be written in English. The UI copy and game data in `lib/games.ts` are in English.

## Commands

- `npm run dev` — dev server (Turbopack)
- `npm run build` / `npm start` — production build / serve
- `npm run lint` — ESLint (flat config, `eslint.config.mjs`)
- `npm run format` — Prettier over the whole repo (config `.prettierrc.json`, ignores `.prettierignore`).
- `npm test` — Vitest, single run (`npm run test:watch` for watch mode). Tests sit next to the code as `*.test.ts` (e.g. `lib/contact.test.ts`); import `describe/it/expect` from `"vitest"`. `lib/test-support.ts` has `installFakeWindow()`, a fake `window` with localStorage (`failReads` and `failWrites` simulate blocked storage) used by the `lib/*.test.ts` files. `lib/games.test.ts` checks `GAMES` against the `readers` in `public/games/bridge.js` and the `av-cover-<id>` rules in `app/globals.css`, and each game's `touch` config: every button code must appear in that game's `game.js` and in the `KEYS` allowlist of `bridge.js`, `a` and `b` must exist, no code may repeat, `move` may only hold arrows and `extra` at most three buttons.
- Dev launch: `.claude/launch.json` has the `arcade-vault` config (`npm run dev`, port 3000).
- Notification hook: `.claude/settings.json` also plays `assets/claudecode-finished.mp3` with `afplay` (macOS) on `Notification`.
- Format hook: `.claude/hooks/format.sh` runs as a `PostToolUse` hook (`Write|Edit`, in `.claude/settings.json`). It runs Prettier on the written file, then `eslint --fix` for `.ts/.tsx/.js/.jsx/.mjs/.cjs`. Remaining ESLint errors exit 2 so Claude sees them. Skips `public/games/`, `references/`, `.claude/` and build output.

## Architecture

- `app/` — App Router. Routes: `/` (landing), `/library` (game library), `/game/[id]` (detail), `/game/[id]/play` (player), `/about` (About + contact form), `/login`, `/hall-of-fame`, plus the API routes `POST /api/contact` and `GET /api/health/supabase`. Main files: `library/library.tsx`, `game/[id]/page.tsx` with `game-stats.tsx` and `game-scores.tsx`, `game/[id]/play/` (`game-player.tsx`; on a touch device, `(pointer: coarse)` through `useCoarsePointer`, it hides the HUD, shows a thin Pause and Exit row above the CRT bezel and draws `TouchControls` (the Gamepad MK-II pad, SPEC 13) right below the CRT bezel, never over the canvas, only while the game is playing, loaded and the final-score modal is closed; SPEC 12), `hall-of-fame/hall-of-fame.tsx` (game tabs that wrap, SPEC 07) and `login/auth-card.tsx`. Anything that means "back to the library" links to `/library`; the logo links to `/`.
- `app/_home/` — landing sections, one file each: `hero`, `features`, `games-rail`, `stats`, `activity`, `pricing`, `final-cta`, plus `silhouettes`, `section-head` and `reveal` (client wrapper that fades a section in once, using `IntersectionObserver`). `hero` and `pricing` read `useSession` to hide "Create account" and turn "Start free" into "Play now". `stats` and `pricing` are static marketing copy; `activity` shows real scores. The `_` prefix keeps the folder out of routing. Landing CSS is `av-home-*` in `app/globals.css`, ported from `references/templates/home-about/`. `games-rail` shows the first five games, hides the `+N more` line when there are none, and its big tile fills the row when it is the only game.
- `app/about/` — About page: `highlights`, `divider` and `contact-form` (client; `ContactSection` validates with `validateContact`, posts JSON to `/api/contact`, shows the `[ERR]` line on failure and the `VAULT-OS // TERMINAL` screen on success). It reuses `Reveal` from `app/_home/`. CSS is `av-about-*` in `app/globals.css`, ported from `references/templates/home-about/`.
- `app/api/contact/route.ts` — `POST` Route Handler that emails the contact form through Resend. Order: parse JSON (400), honeypot field `website` (200, no email), `validateContact` (400 with `fieldErrors`), env check (500), Resend send (502 on error). `from`, `to` and the key come only from env vars; `replyTo` is the visitor's email. Plain-text body. `GET` answers 405.
- `app/api/health/supabase/route.ts` — `GET` Route Handler that checks the Supabase connection by running `select id from games limit 1` through the server client (5 s timeout), so it proves the URL, the key and the `games_and_scores` schema. Answers `200 { ok: true }`, or a generic `500` with no URL, key or stack (details go to `console.error`). It uses `await connection()` and exports neither `runtime` nor `dynamic`, because `cacheComponents` rejects both. Other methods answer 405.
- `components/ui/` — shared UI primitives (`basics.tsx` has `cx` and base components; `interactive.tsx` has client components such as `Input` and `SearchBar`; `game.tsx` has `GameCard`, `CoverArt`, `HUD`, `CRTScreen`, `Podium`, `Leaderboard`; `navbar.tsx` has the Nav with the credit balance and calls `purgeRemovedGameScores`; `touch-controls.tsx` has `useCoarsePointer` and `TouchControls`, the Gamepad MK-II pad right below the CRT screen: a shell, a four-key D-pad with hub and pulsing gem where unused directions are drawn disabled and without `data-key`, round B (always cyan) and A (game accent) with a dashed ring while pressed, and small pills for `extra`, in the centre of the shell on a wide screen and in a full row under the pad below 620 px; SPEC 12 for the behavior, SPEC 13 for the look; CSS is `av-touch-*`, ported from `references/gamepad-assets/`). Per-game cover art is CSS only: `av-cover-<gameId>` in `app/globals.css`. They use `av-*` CSS class names defined in `app/globals.css`.
- `lib/` — client-side data layer, all stand-ins for a future backend:
  - `games.ts` — static `GAMES` catalog (Asteroids, Drop, Brick Buster and Snake: SPEC 08 cut it to Asteroids, SPEC 09 brought Drop back, SPEC 10 brought Brick Buster back and SPEC 11 added Snake as a new game, not a restore of the archived `serpent`), `CATEGORIES` (built from `GAMES`, so it is `All`, `Shooter`, `Puzzle` and `Arcade`), `getGame`. Accents: cyan, magenta, yellow, green. `difficulty`, `plays` and `tags` feed the detail stat strip (`plays` is mock data). `src: null` means a game is listed but not playable yet; no entry has it now. The optional `touch` field (`TouchControls`: `move`: the D-pad directions the game uses, `a`: main action, `b`: second action, optional `extra`: up to three small pills; each is a `TouchButton { code, label, name, repeat? }`) describes the on-screen buttons of a game; `code` is a `KeyboardEvent.code` the game already handles. `repeat: true` makes the host resend `keydown` while held (after 250 ms, every 90 ms) for games that move once per keydown, like `drop`. All four games have it (SPEC 12).
  - `games-archive.ts` — `ARCHIVED_GAMES`: the six games removed by SPEC 08 that have not come back (serpent, muncher, invaders, rocks, froggy, pixel-duel; `drop` returned with SPEC 09 and `brick-buster` with SPEC 10; `snake` of SPEC 11 is a separate game, so `serpent` stays here), kept as data and imported by nothing but its test. To bring one back, move its entry to `GAMES`, add a migration that inserts its `games` row and, for a playable one, check its folder in `public/games/`, its `readers` entry and its `av-cover-<id>` rule.
  - `session.ts` — fake auth in localStorage (`arcade-vault:session`), exposed via `useSession` (`useSyncExternalStore`). Guests are named `GUEST`.
  - `credits.ts` — per-device credit counter in localStorage (`arcade-vault:credits`, starts at 3), exposed via `useCredits`, `spendCredit`, `insertCoin`. The player spends one credit per game start (mount and "Play again"); at 0 it shows `INSERT COIN` instead of the game. The Nav shows the balance.
  - `scores.ts` — per-game leaderboards in localStorage (`arcade-vault:scores:<gameId>`, top 50). `useScores` subscribes to a custom `arcade-vault:scores` event plus `storage`. Cross-game helpers for the landing: `useAllScores`, `latestScores`, `topPlayersToday` (best score per player, local calendar day) and `timeAgo`. `purgeRemovedGameScores` removes the lists of games that are not in `GAMES` (SPEC 08); `components/ui/navbar.tsx` calls it once per page load. It only looks at `arcade-vault:scores:*` keys, never at the session or the credits.
  - `contact.ts` — `LIMITS` (name 80, email 254, message 2000) and `validateContact`. Pure functions shared by the contact form and `POST /api/contact`; the route is the authority.
  - These modules carry `BACKEND:` comments marking where the real API or Supabase calls should replace the localStorage code. Keep the exported function signatures stable when swapping. `lib/supabase/` is the foundation for that swap. Only `leaderboard.ts` and the health route use it so far (SPEC 06, SPEC 08); auth and credits are future specs, and the local `scores.ts` still feeds `/library`, `/game/[id]` and the landing.
  - `leaderboard.ts` — global scores in Supabase: read in SPEC 06, written in SPEC 08. `fetchTopScores(gameId)` returns the top 50 of `scores` as `{ ok: true, entries: ScoreEntry[] }` or `{ ok: false }` (never throws); `rowToEntry` maps a row to `ScoreEntry`. `/hall-of-fame` reads with `fetchTopScores`, with loading, `[ERR]` + `Retry` and empty states and no localStorage fallback. `submitScore({ gameId, player, score })` inserts one row from the browser with the publishable key and resolves `true` or `false` (never throws); `toScoreRow` trims the name and cuts it to 20 characters, and rejects an empty name and a score that is not an integer from 0 to 9,999,999. `game-player.tsx` calls it after the local `saveScore`, with `SAVING…`, `SCORE SAVED` and an `[ERR]` line when it fails (the local copy is kept). The name is free text because there is no real auth yet, so the ranking can be forged by calling the REST API directly. `/library`, `/game/[id]` and the landing still read the local `useScores`.
- `lib/supabase/` — Supabase connection only (SPEC 04). `env.ts` has `getSupabaseEnv`, which reads and validates the two public variables and throws an error naming the missing one. `client.ts` exports `createClient()` for Client Components (`createBrowserClient`). `server.ts` exports async `createClient()` for Server Components and Route Handlers (`createServerClient` with `await cookies()`). Both create the client inside the function, never at module load. There is no `proxy.ts` and no service role key yet.
- `supabase/migrations/` — SQL migrations, versioned in git and applied with the Supabase MCP (`apply_migration`). The file name carries the version that Supabase assigns (check `list_migrations`). Six so far. `20261019092211_games_and_scores.sql` (SPEC 06) creates `games` and `scores` with RLS on and `select` policies, and seeded them with invented data. `20261019103546_save_scores.sql` (SPEC 08) deleted that seed and every game except `asteroids`, and added the `insert` policy on `scores` (player 1 to 20 characters after trimming, score 0 to 9,999,999; the foreign key keeps scores to games that exist in `games`). `20261019103728_least_privilege_grants.sql` revokes every privilege of `anon` and `authenticated` on both tables and grants back only `select`, plus `insert` on `game_id`, `player` and `score` of `scores`, so `update`, `delete` and `truncate` are not granted at all and the browser cannot set `id` or `created_at`. `20261019184002_add_drop_game.sql` (SPEC 09) inserts the `drop` row in `games`, the same values as the SPEC 06 seed. `20261019230130_add_brick_buster_game.sql` (SPEC 10) does the same for `brick-buster`. `20261020000246_add_snake_game.sql` (SPEC 11) inserts the `snake` row. `scores` now holds only scores that players saved. Adding a game to `GAMES` needs a new migration that inserts its `games` row; `lib/leaderboard.test.ts` rebuilds `games` from the migrations and fails when it differs from `GAMES`. Known and not ours: `public.rls_auto_enable()` is a `SECURITY DEFINER` function that `anon` and `authenticated` can execute (advisor warning), pending its own spec.
- `public/games/<id>/` — playable games are static HTML/canvas copies of sibling projects, embedded in the host page via iframe. They are not part of the React build. `asteroids`, `drop`, `brick-buster` and `snake` are in the catalog (`snake` is not a copy: it was written for SPEC 11); the folder of `rocks` stays on disk, unlisted, until that game returns from `lib/games-archive.ts`. `asteroids` has an 800×600 canvas that was cut at the right edge on a phone, so its `index.html` (not its `game.js`) has an inline `fitToFrame()` that scales the canvas with CSS `zoom` and never up (SPEC 12). `drop` is bigger than the 4:3 CRT frame (its page is about 662×656 px), so its `game.js` has `fitToFrame()`, which scales the page down with CSS `zoom` to fit the iframe and never scales up; a game whose page does not fit the frame needs the same. Its keydown handler also calls `preventDefault` on the arrow keys so they do not scroll the host page. `brick-buster` has an 800×600 canvas that is cut at 375 px, so its `game.js` has the same `fitToFrame()`, sized from the canvas and not from the page because its controls guide and mute indicator sit outside the canvas; its keydown handler calls `preventDefault` on `ArrowUp` and `ArrowDown` outside the menu. Its own `blur` handler pauses it when the iframe loses focus, so after the host Pause and Resume it stays paused until P or Esc. `snake` has a square 600×600 canvas (`aspect: "1 / 1"`, 20×20 grid) and the same `fitToFrame()`, sized from the canvas; it uses `requestAnimationFrame` and `performance.now()`, so the host pause freezes it, and it does not pause on `blur`. Its `sprites.js` and `fruits.png` are third-party sprites ripped from Google Snake (spriters-resource), with the atlas names fixed to match the image; replacing them with original art would need its own spec. Its reader returns `lives: null` and `over: state === 'gameover'`, which is also true after a win.

## Environment variables

Copy `.env.template` to `.env` (git-ignored). Server only, never prefix with `NEXT_PUBLIC_`:

- `RESEND_API_KEY` — Resend API key.
- `CONTACT_TO_EMAIL` — inbox that receives contact messages.
- `CONTACT_FROM_EMAIL` — sender, e.g. `Arcade Vault <onboarding@resend.dev>`. The Resend sandbox sender only delivers to the email that owns the Resend account.
- `SUPABASE_DB_PASSWORD` — database password, reserved for the Supabase CLI. No code reads it.

If any of the first three is missing, `POST /api/contact` answers 500.

Public by design (the `NEXT_PUBLIC_` prefix is intended here; security comes from RLS, not from hiding them):

- `NEXT_PUBLIC_SUPABASE_URL` — project URL, `https://<project-ref>.supabase.co`.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — publishable (anon) key. Never put the service role key in a `NEXT_PUBLIC_` variable.

If either is missing or the URL is not `http(s)`, `getSupabaseEnv` throws and `GET /api/health/supabase` answers 500. `NEXT_PUBLIC_*` values are inlined at build time: restart `npm run dev` after editing `.env`, and rebuild for production.

## Skills

Use **/spec** to write a spec and **/spec-impl** to implement it. Both live in `.agents/skills/` and are symlinked from `.claude/skills/`; `skills-lock.json` pins them to `Klerith/fernando-skills`. `specs/.spec-config.yml` sets `AutoCreateBranch: true`, so `/spec-impl` creates `feature/<slug>` (or `bugfix/`, `hotfix/`) without asking. Specs are `specs/NN-<slug>.md` (01 to 12 so far); a spec goes from Approved to Implemented and its acceptance criteria are ticked as each step is done.

Use **/frontend-design** to scaffold and manage frontend components and architecture.

Use **/add-game** to add a playable game with its global leaderboard. It takes a folder of `references/started-games/` or a new game idea, asks the game-specific questions and writes `specs/NN-<id>-game.md`; the implementation then goes through `/spec-impl`. The skill lives in `.agents/skills/add-game/` (`SKILL.md`, `contract.md`, `spec-template.md`), symlinked from `.claude/skills/`.

Use **/spec-impl-game** instead of `/spec-impl` for an approved game spec (`specs/NN-<id>-game.md`). It reads `.agents/skills/spec-impl/SKILL.md` and follows it unchanged (same Approved gate, branch, step-by-step pauses and ticking, never commits). It stops with a pointer to `/spec-impl` when the spec does not add a game. After the last step it runs the **skin-designer** agent on `<id>`, waits for it, and only then runs the **mobile-porter** agent on `/game/<id>` and `/game/<id>/play`: never in parallel. Then it runs lint, test and build again and re-checks the criteria the agents could have broken. The skill lives in `.agents/skills/spec-impl-game/`, symlinked from `.claude/skills/`.

Use the **game-planner** subagent (`.claude/agents/game-planner.md`) to decide which game to add next. It scores ideas against the platform (bridge, CRT frame, catalog balance), and records every suggestion, decision and reason in `references/game-suggestions-todo.md`, which is its only memory. It never writes code or specs; its last step points to `/add-game`.

Use the **game-jam** subagent (`.claude/agents/game-jam.md`) when you have a game in mind and describe it. It writes at least two complete `Draft` specs (`01-<id>-game.md` for the base game, `02-…` for an extension, an optional `03-…`) in `specs/game-jam/<id>/`, modeled on specs 05, 10 and 11. Your description is the source of truth: it flags platform clashes without redesigning the game, and when something essential is missing it writes nothing and returns questions. It fills the small details `/add-game` would ask (id, accent, difficulty) and marks those as game-jam decisions to review. It writes nothing outside `specs/game-jam/<id>/`: to implement one, review it, set it to `Approved`, and move it to `specs/NN-<slug>.md` for `/spec-impl`.

Use the **skin-designer** subagent (`.claude/agents/skin-designer.md`) to check that the games you name have the skins `classic` (default), `retro` and `neon` and a light/dark toggle, and to add what is missing. It works only on the games you tell it, never on the rest of the catalog. Each skin must look good in both themes, dark first (contrast check plus screenshots). It edits only `public/games/<id>/` and keeps `references/game-with-themes.md`, its only memory, with one row per game you asked for; it never changes gameplay, the bridge, the readers or the host.

Use the **mobile-porter** subagent (`.claude/agents/mobile-porter.md`) to check that the routes you name look and work well on a phone browser (375×812, 412×915, landscape) without changing the desktop look, and to fix layout and CSS problems. It follows the rules of `specs/12-touch-controls.md`, works only on the routes you tell it, and keeps `references/mobile-porting.md`, its only memory, with one row per route. It edits only `app/globals.css`, layout markup in `app/` and `components/ui/`; it never touches `public/games/`, the bridge, `lib/` or behavior, and anything beyond CSS/layout goes to a `/spec`. There is no PWA, so "mobile app" means the mobile browser.

### Host ↔ game bridge

`public/games/bridge.js` is loaded by each game's `index.html` **before** its own scripts, with `data-game="<id>"` on the script tag. It:

- Polls the game's top-level globals every 200 ms (per-game `readers` map) and posts `{source: 'arcade-vault-game', type: 'state', game, state: {score, lives, level, over}}` to the parent window.
- Pauses/resumes on host messages `{source: 'arcade-vault-host', type: 'pause' | 'resume'}` by freezing `requestAnimationFrame` and `performance.now`.
- Turns host messages `{source: 'arcade-vault-host', type: 'key', code, down}` into a `keydown` (`down: true`) or `keyup` `KeyboardEvent` on `document` with `bubbles: true`, for the touch controls. Only `e.source === window.parent` is accepted, and only codes in the `KEYS` allowlist (`ArrowUp/Down/Left/Right`, `Space`, `Enter`, `KeyC`, `KeyE`, `KeyP`, `Digit1` to `Digit3`); any other code is ignored. A new touch button needs its code in that table. The host owns key repeat, since a synthetic `keydown` does not auto-repeat, and releases every held key on `pointerup`, `pointercancel`, `lostpointercapture`, page hidden, host pause and unmount. The touch buttons call `preventDefault` on `pointerdown` and `mousedown` so the tap does not take the focus from the iframe: `brick-buster` pauses on `blur`.

Adding a new playable game requires: its folder under `public/games/`, the bridge script in its `index.html`, a `readers` entry in `bridge.js` that matches the game's global state variable names, a `src` and a `touch` config in `lib/games.ts` (`lib/games.test.ts` fails without it, and when a code is not in the game's `game.js` or in the bridge allowlist). Any new catalog entry also needs an `av-cover-<id>` rule in `app/globals.css`, and a migration that inserts its row in `public.games`, because saved scores have a foreign key to it.
